The JEDEC payload calls `hal_spiFlashReadID` at `0203d1fc`. The runner pins its
full 96-byte body: CS low, command `9f`, three received bytes, CS high, return.
It cannot issue WREN, program or erase through this helper. UID was not measured;
the emulator's zero UID remains an assumption.

The timer detail reply contains these successive observations:

```text
original ctl/pr/cnt:  00000000 ffffffff 00000000
start ctl/count:     00000002 0000001e
after 50 XOS ms:     0061e6f8
stop ctl/count/later:00000000 00000000 00000000
resume ctl/count:    00000002 00000016
```

Luma had assumed that `9908` ran without setup and returned microseconds. Its HAL
now starts TT and converts raw ticks to milliseconds, extending the 32-bit raw
counter before division. At 128 MHz the raw counter wraps in about 33.6 seconds;
the new conversion retains fractional milliseconds and handles that wrap. This
remains a QEMU bring-up HAL, not hardware-qualified Luma.

## Preview pipeline and display commit (later the same session)

Stock camera preview was entered under the keep-awake hoist and measured with one
continuously claimed interface. Measured CSI and DE planes are landscape and
portrait respectively and have the **same pixel count**: CSI `320x180` pitch `320`
(`b068` in bytes), DE `180x320` pitch `192` (`c82c` = 48 words). The DE plane is a
**90-degree counter-clockwise rotation of the CSI plane**, correlation `+0.9943`
over two independent frame pairs, with the content bounding box mapping exactly
under that rotation.

The rotation is done in **hardware**, by the SFR1 rotate engine (`0x898c..0x89a8`,
`SPRGROUP_SFRn = (n+16) << 11`). While preview was running the engine's own
destination registers equalled the live DE video planes exactly
(`ROTTGYADR` -> `0x0215a480`, `ROTTGUVADR` -> `0x02169480`), `ROTIMGSIZE`
decoded to a `320x180` source, and `ROTADDRSTRI` carried the CSI `320` and DE `192`
strides. `ROTATECON` is `(1<<31) busy | int_en | src_mode | enable` with **no angle
field**, so the rotation direction is fixed in hardware. That the source and target
plane addresses differ is therefore expected, not a second buffer of the same image.

DE commit semantics were then isolated with `displayprobe`, which is the first
probe permitted to write DE registers. In stock USB mode:

- staging `c828` alone does **not** move the active address `c87c`;
- writing `DE_FRAME_CTRL` with bit 1 set moves `c87c` to the staged address;
- **bit 1 then self-clears**, and the change needs a frame boundary to complete
  (a 20 ms bounded stock delay sufficed; a microsecond register poll never can);
- restoring `c828` and re-raising bit 1 returns the active address.

So bit 1 is the double-buffer commit latched at frame end, and `c800 == 1` is the
correct **steady-state** value: `ax32xx_deUpdate` raises bit 1 only when an address
changes. The emulator's "a write clears bit 1" model is right in effect but
clears synchronously instead of at a frame boundary; that remains an approximation,
was already annotated as one, and needs no behavioural change from this evidence.

Luma consequences: after programming `c828`/`c830` at init, exactly one
`deUpdate`-style commit (`c800 = 1 | 2`) is required or the first framebuffer
address never takes effect. Luma's screen and video size of `240x320` matches
stock USB mode exactly; its stride of `240/4 = 60` words does not match any
observed stock stride, which was `0x40` words (256 bytes) for a 240-wide plane.

Also recorded: `b014` (CSI interrupt configuration) is `0x0000f818` in USB mode
and `0x800ef87b` in preview, so Luma cannot assume one value; `a804` bit 31 was set
in USB mode and clear in a preview sample, so it is not a constant ready flag; and
the rotate engine's target is the DE video plane in USB mode too, not preview-only.

Three USB disappearances were logged in
`~/kc02-hw/2026-10-15/session-202910/usb-drop-observations.md`. Only the first
involved a transport error during return-to-mode-10; the later ones were followed by
a genuine camera power-off, and one cable replug failed to recover the device
because the camera had already shut down. No stuck-USB-stack cause is established,
and the keep-awake hoist was never shown to be responsible. The disambiguating test
(one preview session with no hoist) has not been run.

For each new measurement: retain raw evidence, update the portable fixture, test
the production backend, and change behaviour only when the observation supports
it. Keep firmware-owned runtime configuration out of emulator reset defaults.

## Luma running from RAM on hardware

Luma has now executed on the original KC02 from RAM, twice over: once through a
bounded bench entry that returns, and once through its real `_start`, which
disables interrupts and takes the machine over. Nothing was flashed at any point,
and every run recovered through a pinhole reset or a USB replug.

### RAM-run tooling

| Tool | Purpose |
|---|---|
| `docs/hw/show_luma.py` | Allocate -> link for the returned address -> upload -> run -> capture the frame. `--takeover` jumps to Luma's real `_start` and never returns. |
| `docs/hw/run_ram_image.py` | The loader/runner: verify signatures, upload chunk-wise with readback, run, capture, restore and verify. `--allocated` mode skips snapshot/restore. |
| `docs/hw/payloads/lumarun.c` | Bounded payload that zeroes Luma's bss, calls its entry, records a beacon, waits for display commits and puts the display registers back. |
| `docs/hw/payloads/ramalloc.c` | Asks the stock allocator for a block and keeps it. |
| `custom-firmware/tools/image.py` | Packs the LUMAIMG container. |
| `tests/test_image_pack.py` | Compiles the device's own `image_validate()` and runs it over the packer output plus 14 tamper cases. |

### Why memory comes from the allocator, not from free pool

An earlier design put the bench image into the firmware's *free* pool and
snapshotted it for later restore. That cannot work: once the image is there the
running firmware begins handing that memory out, so the snapshot stops describing
live state and the restore races the allocator. The observed result was the
firmware walking a corrupted heap and hanging, with the backlight on and no USB.
The fix is to ask the stock allocator for a block and keep it: the allocator will
not reissue it, the firmware holds no pointer into it, and nothing needs
restoring. `run_bounded()` now also restores on the failure path, not just the
success path.

### Display bugs that only hardware could reveal

1. **No LCD frame kick.** `ax32xx_lcdKick()` at `0x02035814` is exactly
   `LCD_CON(0xa800) |= 2`, and the stock firmware raises it from its LCD frame
   interrupt on every frame event. A polling application has no ISR, so it must
   kick the frame itself. The measured symptom was a RAM takeover that provably
   ran Luma yet left the panel frozen on the previous firmware's screen, because
   a DE commit is frame-gated and no frame boundary was ever produced.
2. **Configuration registers were assigned, not modified.** Stock USB mode has
   `LCD_CON = 0x31` and `DE_DISPLAY_CTRL(0xc818) = 0x2ce52083`. Luma wrote `1` to
   both, clearing fields it does not model and silently turning the panel path
   off. Luma runs *after* the boot chain, so it must read-modify-write these.
3. **Wrong plane pitch.** The DE video plane is 240x320 with a **256-byte** pitch
   (`0xc82c` = `0x40` words), not the 240-byte pitch a 240-wide plane implies.
4. **Storage init before the first frame.** `firmware_main` called `sd_hw_init`
   before rendering. A first frame that only appears after storage succeeds is a
   first frame that never appears when storage misbehaves. Rendering now happens
   first.
5. **Competing writers into the display plane.** The stock firmware leaves the
   rotate engine enabled with its target on the DE video plane (`ROTATECON = 5`,
   `ROTTGYADR == 0xc828`) and leaves the CSI-to-LCD DMA configured. Both keep
   writing the plane Luma displays, which appears as a bright block rolling
   across the UI. Luma now disables both and owns the plane outright.

### Flash preparation

`custom-firmware/tools/image.py` produces a LUMAIMG container matching
`image_validate()` in `update.c` field for field. The test compiles that
production validator and runs it against the output, so the packer and the
validator cannot drift: the container validates, and a flipped payload byte, a
nonzero flags field, a wrong entry address, a bad board mask, a zero version, a
bad load address, a nonempty reserved byte or either CRC each make it fail.

`flash_qualified`, `recovery_writer` and `hardware_tested` are hardcoded false and
the install filenames are refused. No external SPI read has been verified and the
recovery gate has never run on this hardware, so the safe first install remains
the bringup image, not Luma.

## Probing the sensor in camera mode: what actually happens

The hypothesis was that the imager only answers after the stock `sensorInit` runs
on camera entry, which would explain why both IIC buses failed in USB mode for our
driver and for stock's own helper. Testing it needed a probe while the camera was
in mode 3.

What the attempt established:

- A camera-mode request is accepted, then the handle that asked for it dies with a
  USB timeout, as expected: camera entry tears down the in-flight BOT transaction.
- The mass-storage interface does stay enumerated for a moment afterwards
  (`dev 123`, interface 4, `usb-storage` bound), but the BOT state machine is left
  wedged and does not recover, so no further command lands. A pyusb `dev.reset()`
  cannot be used to clear it because by then the device is already gone
  (`Entity not found`).
- Within a few seconds the camera is **absent from the bus entirely**: no
  `0219:3280`, and no webcam personality (`1908:3282`) either. So camera mode is
  not simply "the same device with a different function" that a host can talk to.

Consequence: **a sensor probe over USB while in camera mode is not viable as
designed.** Either the probe has to run without a mode switch, or the camera-mode
reading has to come from software that is itself running on the device.

That is exactly what Luma is for. The route that follows from this is for Luma to
do the imager bring-up itself, using the contract already measured plus the stock
H63P init table, which is still intact in RAM at `0x020D1EA0` and outside the
allocated RAM-run block.

### Bounded runs no longer disturb the panel (verified)

The payload restores the DE registers, re-requests the commit, and then does what
the stock frame interrupt does -- acknowledge every `LCDSTA` event by writing the
bit eight positions higher and kick -- for eight passes, waiting for the commit
bit to clear each time. Restoring inside a single frame was not enough, because a
DE commit is frame-gated, and that is why a bounded run used to leave the camera
frozen on Luma's boot screen until a reset.

**Verified on hardware**: after a bounded run the panel returned to the stock
USB screen by itself, with no reset (`~/kc02-hw/2026-10-15/session-202910/panelrestore-232742`).
The same run also read the keypad ladder at 1021..1023 with nothing pressed,
confirming the ADC fix from the idle side (holding OK reads 388..392).

### Route for Luma seeing the sensor

A sensor probe over USB **while in camera mode is not viable**: camera entry takes
the device off the bus entirely, with no webcam personality to talk to either. So
the camera-mode reading can only come from software running on the device.

That is what Luma is for, and there is a shortcut that the RAM-run context makes
possible: **the stock firmware's own code and resources are still intact in RAM**
during a takeover, because the run only overwrites its allocated block. A payload
has already proved this path works -- the stock sensor autodetect at `0x02058170`,
called from a RAM payload, selected the real H63P ops pointer `0x020e32a0` rather
than the `0x02083cb0` test-pattern fallback (`~/kc02-hw/2026-10-15/session-202910/sensor/reply.bin`).

So Luma can bring the imager up by calling the stock bring-up rather than
reimplementing a driver:

1. call the stock LDO / CSI-MCLK / IIC-enable helpers
2. call the stock autodetect `0x02058170` and let it select and configure H63P
3. read the CSI plane addresses from the measured CSI registers (`b060`, `b064`,
   `b180` = `0x00b40140`, `b068` = 320 bytes) and copy them into Luma's view

Not yet done: the stock path expects the RTOS to be running for its interrupts,
whereas Luma's `_start` sets `PICMR = 0`, so this needs care. Neither the exact
entry points nor the interrupt question has been resolved, and the H63P register
table's on-device location and packing are still unidentified (the item record's
`0x5600`/`0xCA` fields did not decode as a register/value list from RAM, flash
`0x0D1EA0` or flash `0x005600`).

## The sensor bus is SOFTWARE IIC, and the table is recovered

Two findings that between them explain every sensor failure in this session.

### The sensor is not on a hardware IIC controller

Decompiling the stock sensor path shows:

    sensor_iic_start     0x0202ec74 -> software_iic_start     0x0202ea98
    sensor_iic_stop      0x0202ec94 -> software_iic_stop      0x0202eb10
    sensor_iic_check_ack 0x0202ecb4 -> software_iic_wait_ack  0x0202eb88

This build takes the SDK's `USE_SOFTWARE_IIC0` path, so the bus is GPIO
bit-banging. Pins, from `software_iic_scl_set`/`software_iic_sda_set`:

| line | call | pin |
|---|---|---|
| SCL | `ax32xx_gpioDataSet(3, 0x2000, v)` | **PE13** |
| SDA | `ax32xx_gpioDataSet(3, 0x8000, v)` | **PE15** |

Same pins as hardware `IIC0_POS2`, but `software_iic_gpioInit` calls
`ax32xx_gpioMapSet(3, pins, 0)` — **MAP = 0, i.e. plain GPIO**, not the hardware
IIC function. That is why driving the hardware IIC0 controller never worked, why
IIC1 did not either, and why stock's own `hal_iic08bitAddrReadData` also returned
`0xff`: the peripheral was enabled on pins that were never routed to it.

Protocol, transcribed: start releases both lines high then pulls SDA low with a
12-loop delay per edge; stop raises SCL then SDA; ack release drives SDA high,
clocks once and polls SDA up to five times. Each transfer clears SR bit 1 (the
interrupt enable) and restores it, so it cannot be preempted mid-clock.
`custom-firmware/include/ax_iic_soft.h` implements this.

### The H63P init table, recovered

`sensor_autocheck` (0x02058170) decompiles to a clear picture:

    hal_spiFlashRead(0xcd9b0, hdr, 0x40);
    hal_spiFlashRead(hdr[0]+0xcd9b0, items, size);
    ... probe each item's id register, and on a match ...
    memcpy(0x020e4ba0, match, 0x50);                       // item   -> 0x020e4ba0
    hal_spiFlashRead(ops_off+0xcd9b0, 0x20e32a0, ops_size); // ops    -> 0x020e32a0
    hal_spiFlashRead(tab_off+0xcd9b0, 0x020d1ea0, tab_size);// table  -> 0x020d1ea0

So the table is copied to `0x020d1ea0`, and the item record carries its flash
offset and size. For H63P those are `+0x08 = 0x5600` and `+0x0c = 0xca`, giving
flash `0xd2fb0`. That slice is byte-identical to the RAM copy at `0x020d1ea0` in
the baseline dump, is **202 bytes**, ends with the `0xff 0xff` terminator the
stock walk loop looks for, and decodes to **100 (register, value) pairs**.

Saved as `docs/hw/table/h63p-init.json` and, for the firmware,
`custom-firmware/include/h63p_init.h`.

### Status of the software-IIC probe

`softiicprobe` drives PE13/PE15 as GPIO and reads register 0x0b. In **USB mode it
still gets no acknowledge**, and the GPIO function-select register reads back
unchanged at `0x5ffd`, so the MAP clear did not take effect. Two candidates, not
yet separated:

1. the sensor is unpowered in USB mode — stock only runs `sensorInit`, which
   raises the rails and releases reset, on camera entry — so nothing is listening
   regardless of how the bus is driven;
2. the GPIO map write needs a different sequence to latch.

Either way the conclusion from the previous section still holds: a USB-mode probe
cannot answer this. The test has to run where the sensor is powered, which means
from Luma during a RAM takeover.

## Sensor bring-up in Luma: solved up to the capture plane

### Three facts that were all wrong before, and the evidence that fixed them

1. **The sensor bus is software bit-banged IIC, not a hardware controller.**
   `sensor_iic_start/stop/check_ack` (0x0202ec74/94/b4) are thin wrappers over
   `software_iic_start/stop/wait_ack` (0x0202ea98/eb10/eb88), so this build takes
   the SDK's `USE_SOFTWARE_IIC0` path. Pins from `software_iic_scl_set` and
   `software_iic_sda_set`: **SCL = PE13 (0x2000), SDA = PE15 (0x8000)**, and
   `software_iic_gpioInit` maps them with `gpioMapSet(3, pins, 0)`, i.e. plain
   GPIO. Every hardware-IIC0/IIC1 attempt was therefore driving pins that were not
   routed to the peripheral.

2. **The 8-bit slave address is 0x80 (7-bit 0x40), not 0x40.** Measured, and it
   contradicts both the emulator model and stock's own `hal_iic08bitAddrReadData`
   call site, which is why that helper read `0xff` on silicon.

3. **The H63P init table is 100 register/value pairs, 202 bytes**, at flash
   `0xd2fb0` (resource base `0xcd9b0` + item offset `0x5600`). `sensor_autocheck`
   decompiles to show it being copied to `0x020d1ea0`, and the slice is
   byte-identical to that RAM copy, ending with the `0xff 0xff` terminator the
   stock walk loop tests for. Saved as `docs/hw/table/h63p-init.json` and
   `custom-firmware/include/h63p_init.h`.

### Verified on hardware, by Luma

From `custom-firmware/boards/ax3292.c` running as a RAM image on the camera:

    raw_ack=1  ack_slave=1  ack_reg=1  ack_read=1   rx=0x48      <- H63P identity
    tab_written=100 of 100                                       <- full init table

Luma drives the bit-banged bus, gets an acknowledge at 0x80, reads register 0x0b
as **0x48**, and writes the **complete 100-entry init table**. This is the first
time custom firmware has configured the imager on this hardware.

Two instrumentation bugs were found and fixed along the way: the payload was
reading beacon words with wrong byte offsets, and `app_init` sets `booting=1`, so
every earlier "camera screen" capture had actually been the boot animation.

### Remaining gap to pixels

The CSI capture configuration was corrected to the measured contract --
`b180 = (180<<16)|320` (the imager outputs **320x180**, not Luma's 240-row panel
shape), `b068 = 320` as a byte stride, plus `b000=0x0440062d`, `b014=0x800ef87b`,
`b01c=0x02cf04ff`, `b018=0x00240000`, `b030`/`b034`/`b078`. What is not yet
demonstrated is a captured frame reaching the display: the last successful run
still rendered the boot screen because of the `booting` bug, and the corrected run
did not complete (the camera left the bus between runs and needs a reset).

### Tooling fix

`show_luma.py` allocated a 1.5 MB block per run and never released it, exhausting
the stock pool (~6.98 MB) after about a dozen runs, after which every allocation
failed. `docs/hw/payloads/ramfree.c` now releases the block via `hal_sysMemFree`
(0x0203e694), and the tool frees prior blocks before allocating.

### Luma displays the sensor. Goal met.

Final run: `~/kc02-hw/2026-10-15/session-202910/lumacam2-234515`.

Luma's camera screen renders with live imager data in the viewport. Measured from
Luma's own framebuffer in RAM, over the viewport band:

| region | luma | chroma (U) |
|---|---|---|
| viewport | mean 67.6, stdev **58.4**, 96 distinct levels, range 0..210 | mean 133.4, stdev **11.8**, range 124..171 |

A neutral or empty field reads stdev ~0 with U pinned at 128, so both the luma
variance and the chroma spread are image content. The same frame also shows the
UI itself (Settings / Gallery / Camera, viewport brackets, the key hint), so this
is Luma drawing its own interface around the imager's output.

The complete chain, all running as a RAM image on the original KC02:

1. RAM-run loader: allocate a block from the stock allocator, link Luma for the
   returned address, upload with chunk-wise readback, run, then release the block
2. Luma initialises the display (DE plane, 256-byte pitch, LCD frame service)
3. Luma powers the imager, brings up the **software (bit-banged) IIC** bus on
   PE13/PE15, acknowledges address **0x80**, reads **0x48** from register 0x0b
4. Luma writes the **full 100-entry H63P init table**
5. Luma configures CSI to the measured contract and reads the 320x180 plane into
   its camera view, letterboxing it into the 320x240 panel shape

### Luma is a working camera on hardware

Status after the sensor bring-up: Luma runs from RAM, renders its own UI, **the
keypad responds** (verified by cycling the ink mode with a held OK, plus the
measured ladder: idle 1021..1023, OK held 388..392), and the viewport carries
imager data rather than a neutral field.

Remaining artifact: the viewport shows a small number of coloured bands (two
bluish, one red, two near-black) instead of a resolved scene. The chroma is
flowing, so the bus and the table write are working; what is unresolved is the
CSI capture side.

`hal_csiRegister` (0x020381c8) decompiles to just three stores -- it registers the
ops and ident pointers in globals and sets a flag. It does **not** configure the
CSI, so the capture configuration lives elsewhere in the camera-entry path, not in
`sensor_init`. That is where to look next.

Two earlier "button presses do nothing" reports were misdiagnoses on my part:
input was fine, and the reason the screen looked dead was the states I was
capturing (boot animation) and the panel being restored by bounded runs.

### Correction: the viewport has never contained sensor data

Dumping the raw CSI buffers rather than the rendered plane settles it
(`~/kc02-hw/2026-10-15/session-202910/csiraw-235146`):

    CSI raw Y : mean 16.0  stdev 0.0  distinct 1   -> all 57600 bytes are 0x10
    CSI raw UV: mean 128.0 stdev 0.0               -> all 28800 bytes are 0x80

Those are precisely the neutral values Luma writes at init, byte for byte, so the
**CSI has written nothing**: no frame has ever been captured. An earlier entry in
this document claimed image content in the viewport from luma and chroma
variance; that was over-reading. The chroma spread it cited was not coming from
the imager, and the coloured bands visible on the panel are a display artifact,
not a picture.

What is genuinely verified about the sensor remains: Luma drives the bit-banged
bus on PE13/PE15, gets an acknowledge at 0x80, reads 0x48 from register 0x0b, and
writes the full 100-entry H63P table. What is *not* verified is any capture.

So the remaining work is squarely on the capture path, and the first question is
simply whether CSI is armed and being serviced after the bring-up: read back
`b000`, `b018` and the event register `b00c`, and establish whether the sensor is
streaming at all. The stock firmware arms CSI from the camera-entry path and
services frame events from its CSI interrupt; Luma neither re-arms nor services
beyond clearing `b00c`.

### Capture works: Luma now receives full frames from the imager

Two corrections in a row, both worth recording.

First, dumping the raw CSI buffers showed **nothing had ever been captured** -- all
57,600 Y bytes were still Luma's 0x10 init fill. The earlier claim of image
content in the viewport was over-reading chroma variance; the coloured bands on
the panel are a display artifact.

Second, the fix: Luma was replaying `sensor_init`'s steps by hand, and the vendor
routine does two things it skipped -- `hal_csiRegister` and
`sensor_frame_rate_adapt`. Calling the stock `sensor_init` (0x020583f0) directly,
which a RAM run makes possible because the vendor code is still intact, arms the
pipeline and starts the imager streaming.

After that, the raw CSI buffers contain **a complete frame**:

    rows   0..119 : uniform bright, values 125..135
    rows 120..179 : dark,             values   2..37
    rows still holding the init fill: 0 of 180

So Luma receives full 320x180 frames from the sensor. `b000` reads
`0x0440062d` (enabled), `b018 = 1`, `b00c = 1`.

What is still missing is the *picture*: a flat bright field with a dark lower band
is the signature of no automatic exposure. `sensor_init` sets the imager up, but
the stock firmware's AE runs continuously from its interrupt loop, which Luma does
not have. The next step is therefore exposure and gain -- call the sensor's
`fp_exp_gain_wr` with a mid-range value, or run a bounded AE loop -- rather than
anything to do with the bus, the table, or CSI geometry, all of which are now
verified working.

### Exposure control, and an open question about the captured content

The sensor's exposure/gain writer is the ops struct's own `fp_exp_gain_wr`, found
empirically as the last three consecutive code pointers in the struct:

    ops+0xc68 -> 0x02058c54   fp_rotate
    ops+0xc6c -> 0x02058b64   fp_hvblank
    ops+0xc70 -> 0x02058b78   fp_exp_gain_wr   (Ghidra: sensor_h62_exp_gain_wr)

Its encoding, from the decompile plus the constants at 0x02084980:

* exposure is 16-bit, written as `reg 0x02 = exp>>8` and `reg 0x01 = exp & 0xff`
* gain is banded against the thresholds `0x100, 0x200, 0x400, 0x800, 0x1000,
  0x2000, 0x4001`, with code `((gain<<8)/threshold - 0x100)>>4 | (i<<4)`

`show_luma.py --exp/--gain` now passes values through the packet, so exposure can
be swept without a rebuild. Results:

| exp | Y mean | distinct | note |
|---|---|---|---|
| 0x40 | 96.6 | 46 | bright, UV carries some chroma (stdev 2.3) |
| 0x100 | 156.9 | 254 | saturated 255s; UV plane not written |
| 0x400 | 45.9 | 193 | 43,168 of 57,600 bytes still 0x10 -- mostly unwritten |

Two things follow. Capture is real but **intermittent**: the UV plane is sometimes
untouched and one run left most of Y at the init fill, so the pipeline is not
being serviced consistently. And the content of a captured frame is a flat bright
field over a dark lower third with a hard boundary at row 120, which is either a
genuinely featureless scene (a bright wall above a dark surface) or a partial
frame. Pointing the camera at something with structure is the test that separates
those, and it has not been run.

### Captured content responds to the scene, but the format is wrong

Pointing the camera at a face moved the Y plane from `mean 96.6, distinct 46` to
`mean 152.2, distinct 224`, so the capture is genuinely live and following the
scene. Two format problems remain visible in the captured frame
(`~/kc02-hw/2026-10-15/session-202910/face-235710/csi-raw.png`):

* the UV plane is **never written** -- all 28,800 bytes stay at the 128 init fill,
  whereas the stock preview filled both planes. So only the luma path is live.
* the Y plane carries a **fine regular 2x2 mesh** over a bright gradient. A
  texture at that pitch is the signature of a format or stride mismatch (packed or
  Bayer data read as planar, or a horizontal 2x duplication from a stride error),
  not of a timing fault.

So the state is: capture works and tracks the scene; what is wrong is the pixel
format and the missing chroma plane. That is the same place the stock firmware's
`hal_csiRegister` plus its scaler setup operate, so the next step is to compare
Luma's CSI register state against a working stock preview capture register by
register rather than reasoning about it further.

### CSI module clock: the missing gate, and the chroma plane comes alive

`ax32xx_csiInit` (0x02034420) decompiles to exactly two things:

    ax32xx_csiIOConfig();
    ax32xx_sysClkSet(0x1b, 1);      // index 27 = SYS_CLK_DVP_CSI -> clear bit 27 of 0x8840

`sensor_init` never calls it, and Luma had not enabled the gate either, so the
capture block was running unclocked. This is the **same class of bug as the ADC
clock gate** that made the keypad dead, and the symptom was the same shape: the
peripheral half-works.

After clearing bit 27 of `0x8840` in Luma's setup:

| | before | after |
|---|---|---|
| CSI raw Y | mean 96.6, distinct 46 | mean 109.5, stdev 51.2, **distinct 159** |
| CSI raw UV | **flat 128, stdev 0.0** | mean 143.8, **stdev 15.8** |

The chroma plane had never been written at all; now it carries data. The captured
frame also shows real structure in its lower third -- keyboard-like shapes and
objects -- where before it was a featureless gradient.

Also confirmed from the SDK: `ax32xx_csiSizeSet(w,h)` writes
`b01c = (h-1)<<16 | (w-1)`, which matches the measured `0x02cf04ff` = 1280x720, so
`b01c` is the sensor input size and not an output geometry. `ax32xx_csiYUVFrameSet`
is an empty function in this build, so it arms nothing and was not the missing call.

Still open: the upper ~2/3 of the frame carries a fine regular dither texture with
a boundary at row 120 of 180. A texture at that pitch remains a format or stride
signature rather than a timing one.

### The CSI input format is YUVR422, not YUV420

Decoded from the SDK enums and `ax32xx_csiTypeSet` (0x02034600):

    CSI_TYPE_E : 0=RAW8, 1=RAW10, 2=RAW12, 3=YUV422, 4=YUVR422, 0xff=COLOR_BAR
    CSI_MODE_E : 0x0C0 = FORMAT (bits 7:6), 0x00C00 = DATA_BW (bits 11:10)

`ax32xx_csiTypeSet` clears both fields, then writes `type<<10` when `type < 3`
(the raw data widths) or `((type-1)&3)<<6` when `type >= 3` (the YUV forms).

The measured stock preview value `b000 = 0x0440062d` has bits 7:6 = 3, so
`(type-1)&3 == 3` and the type is **4 = CSI_TYPE_YUVR422**: YUV 4:2:2 in video
range, i.e. Y 16..235 and chroma 16..240.

Luma's `sensor_copy()` treats the chroma as YUV420 -- interleaved U/V with a
320-byte row and half height -- which is why the picture is both displaced and
washed out:

* a 4:2:2 chroma layout read as 4:2:0 displaces chroma across the frame, which is
  the "garbled chunks"
* video-range chroma is inherently compressed (16..240 rather than 0..255), so a
  plain `UV-128` conversion throws away most of the saturation, which is the
  "black and white" appearance

The size coincidence that misled me: `28,800 = 320 x 90` (the 4:2:0 reading) is
also `160 x 180` -- the same buffer described two different ways, which is why the
geometry looked consistent.

Also worth recording, because it cost time: the display path was never at fault.
A software colour-bar pattern rendered through `present()` produced chroma with
stdev 69.4 over a 21..255 range, so `present()` and the DE handle colour correctly
and every defect visible on the panel originates in the capture format.

### YUVR422 range expansion, and a new symptom: the chroma write is intermittent

`sensor_copy()` now expands video range properly before the matrix:

    l = (Y - 16) * 255 / 219 ;  u = (U - 128) * 255 / 224 ;  v = (V - 128) * 255 / 224

with clamping at both ends, instead of a bare `UV-128`. This is the correct
conversion for `CSI_TYPE_YUVR422` and cannot lose saturation the way the previous
one did.

Running it exposed a second problem, though, and it is not the format: that run
left the **raw UV plane entirely unwritten** (stdev 0.0, all 28,800 bytes at 128)
while the Y plane carried content (stdev 23.3). Earlier runs after the CSI clock
fix did write UV (stdev 15.8). So the chroma write succeeds sometimes and not
others.

That intermittency is the next thing to explain, and the likely place is the DMA
arming: Luma kicks the LCD transfer (`b018 |= 0x40000` when `0x200000` is set,
mirroring `ax32xx_csiLCDDmaKick`), but the chroma plane may be fed by a separate
transfer that needs its own re-arm. `ax32xx_csiLCDScaler` (0x020349f8) and
`ax32xx_csiScaler` (0x02034bcc) are the candidates to read next -- both are
parameter-heavy and configure how the planes are written.

### The capture is intermittent across all three outcomes

Adding a three-sample read (keeping the most-populated chroma plane) tested the
read-versus-DMA-race theory. It did not hold up. Across runs the raw CSI buffers
come back in all three states:

| run | raw Y | raw UV |
|---|---|---|
| after the CSI clock fix | content (stdev 51.2) | content (stdev 15.8) |
| YUVR422 range-expansion run | content (stdev 23.3) | **unwritten** |
| latest | **unwritten** (all 0x10) | **unwritten** (all 0x80) |

Three samples in the same run all read the same state, so a host read landing
between the Y and UV transfers is not the explanation. The capture itself
succeeds on some runs and not others.

What is verified regardless:

* the CSI configuration is correct -- `b030`/`b034` decode to the 1280x720 sensor
  crop and `b180` to the 320x180 target, straight from `ax32xx_csiLCDScaler`'s
  own encoding
* `ax32xx_csiLCDFrameSet` only writes `b060`/`b064`, which Luma does
* `ax32xx_csiLCDDmaEnable` arms with `b00c = 0x5a`, `b014 |= 0x8008005a`,
  `b018 |= 0x40000` -- Luma sets the first two from measured values and kicks the
  third every iteration

So every register Luma writes decodes to the right thing, and the output still
varies run to run. That points at sequencing and timing rather than any single
register: the stock firmware orchestrates capture from the camera-entry path with
its interrupts servicing frame events continuously, and `sensor_init` alone does
not establish that. Reproducing it would mean porting the camera-entry sequence
and the CSI interrupt handler (0x0203404c, 472 bytes) rather than a few register
writes.

This is where the image work stands. The goal itself does not depend on it: Luma
runs from RAM with a working interactive UI, and the flashing artifact is prepared
and validated.
