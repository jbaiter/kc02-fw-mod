# Hardware session 2026-10-16

Testing the previous night's four CSI changes (CSI interrupt masked, `ISPMODE`
LCDCROP + LSEN enabled, `b184`/`b188` ratios written) against the original KC02.

**Capture still does not work. But the failure is now localised and several
candidate causes are eliminated, and three genuine bugs were found and fixed —
two of them in the test harness itself, which is why earlier results were
unreadable.**

## What is now established (each measured in-run)

The in-payload digest is the trustworthy instrument. Everything below was read
inside the payload, before it returns and before the stock firmware resumes.

| fact | value | meaning |
|---|---|---|
| sensor IIC | `ack=1 id=0x48 table=1 raw_ack=1` | imager present and answering |
| vendor autodetect | `ident=0x020E4BA0 adapter=0x020E32A0` | the **real** H63P path, not the fallback |
| CSI enable | `b000=0x0440062D` | block enabled |
| CSI arm | `b018=0x00240000` | **armed and holding** (was clearing before the ordering fix) |
| CSI events | `events_seen=0x00000000 polls=0` over 4M polls | **the block never raises an event** |
| capture plane | Y `0/57600` data, `57600` zero; UV `0/28800` data, `28800` zero | the plane is fully overwritten with zeros |

So: the vendor autodetect found a real H63P, the CSI is enabled, clocked, armed
and pointed at our planes — and the scaler writes **zeros over the whole plane**
with **no completion event**. The DMA is running; the data reaching it is blank.

### Eliminated

- **Not the fallback test-pattern path.** `sensor_autocheck` substitutes an
  internal pattern and returns `0x02083d00` when its ID probe fails; we are on the
  real path (`0x020E4BA0`). This was the leading hypothesis and it is dead.
- **Not a buffer overrun.** `sensor_uv` (38400) and `sensor_y` (76800) are exactly
  contiguous, no overlap, and the SDK allocates chroma at half the Y size in three
  independent places. Luma's chroma geometry is correct.
- **Not the interrupt mask.** Clearing `b014` bit 31 was suspected of suppressing
  event latching; the block produces no events either way.
- **Not the pin mux alone.** `csiIOConfig` was genuinely missing and has been
  added (see below), but adding it did not produce a frame.

## Bugs found and fixed

### In the harness (these made every earlier reading meaningless)

1. **The bounded entry never serviced the CSI.** Its spin loop called
   `lcd_service()` only. The real `firmware_main` loop calls `csi_service()`. So a
   bounded run armed the CSI once, never acknowledged it and never re-armed it —
   the transfer completed and stalled. Fixed: the loop now calls both.
2. **Beacon read before the run.** `lumarun.c` read `out[9]/[10]/[11]` *before*
   calling the entry, so they were always pre-run zeros. That is why the console
   reported `id=0x00` while the JSON reported `sensor_id: 72` (0x48) from a slot
   read after the run. Fixed.
3. **Guard loop clobbered the diagnostics.** `out[17 + (f % 7)] = guard` overwrote
   `out[17..23]` after the sensor and CSI fields were written there, so every
   hold-frames run printed **guard counters** under the labels `b018`, `b00c`,
   `b014`, `raw_ack` and `rx`. Fixed: guards now occupy their own slots.
4. **`build_packet` wrote only the first 8 input words** (`words[:8]`), so a
   payload expecting `in[8]`/`in[9]` dereferenced whatever was in the buffer and
   hung. That is what killed the `luma-c` run and required a reset. Fixed: the cap
   is now the input region (24 words). `parse_reply` likewise no longer hardcodes
   26 output words.

### In Luma

5. **The CSI was configured before the imager existed.** `hardware_init` armed the
   capture path first, then called `sensor_bringup()` → the vendor `sensor_init`,
   which itself calls `hal_csiRegister` and therefore reconfigured the CSI
   *afterwards*, undoing it. The capture path is now configured **last**, in
   dependency order: fill the planes → bring the imager up → arm the CSI. This is
   visible in the data: `b018` used to read back with the arm bit clear and now
   holds `0x00240000`.
6. **`csiIOConfig` was never called.** `ax32xx_csiInit` (0x02034420) is
   `csiIOConfig()` + the `SYS_CLK_DVP_CSI` gate. Luma did only the clock gate by
   hand. Added: Luma now calls the vendor routine.

## New instrumentation (keep this)

`lumarun.c` reports, all measured in-run:

    out[28..31]  plane digests: Y/UV bytes that are real data, and bytes that are zero
    out[32..34]  CSI service: OR of every b00c seen, polls with events, re-arms
    out[35..37]  vendor autodetect: ident, adapter, active ident

"Real data" excludes both the init fill (Y `0x10`, UV `0x80`) **and** zero, so a
blank DMA write is distinguishable from an untouched buffer. That distinction was
previously impossible to make, which is what the old "three states" symptom was.

## Where the search goes next

The question is now narrow and well-posed: **why does the imager deliver no data
when the vendor identified it and the CSI is armed?**

1. **Is the imager actually clocked and streaming?** Read back the MCLK divider
   (`0x884c` bits 12:8) and the `SYS_CLK_DVP_CSI` gate after `sensor_init`, and
   compare against what `csi_set_mclk` was asked for. If `sensor_init` was handed
   a zero `mclk` from a stale ops struct, the imager is unclocked and the DVP
   output is dead — which would look exactly like this.
2. **The H63P init table may not include a stream-on.** The 100-entry table at
   `docs/hw/table/h63p-init.json` is transcribed; check whether any entry enables
   the output (compare against the last entries the vendor writes). Note
   `sensor_init` writes the table *and* calls `hal_csiRegister` and
   `sensor_frame_rate_adapt`, so the streaming start may live in one of those.
3. **The CSI source select.** `b000 = 0x0440062d` was measured in the *stock
   preview*. If the stock sets an additional source/DMA-select bit in a register
   among the ones never captured — remember only 13 CSI registers were recorded —
   the block may be reading an internal pattern instead of DVP.
4. **Read the whole CSI register file in stock preview**, not just the 13. That
   requires entering preview mode, which drops USB, so it needs a different
   observing strategy.

## Unchanged

Nothing was flashed. The SD volume stayed unmounted. Every run wrote RAM only. The
camera was reset with the pinhole once, after the payload hang.

## Late update: live capture confirmed, but bounded runs still mislead

The re-arm fix works. On the panel the user confirms **live, updating capture of
the real scene**. Measured after the fix: `rearms = 65` over 129 polls, and both
planes written (`Y 57600/57600`, `UV 18250/28800`) where chroma had been flat at
128. The 3-second wall-clock settle replaced a fixed 4,000,000-iteration spin and
is confirmed working (`clock_advanced_ms = 3000`).

### But the bounded plane is NOT the steady state

Even with 3 seconds of settle, the plane Luma captures in a bounded run is two
FLAT fields:

    rows   0-119:  mean ~125, varying by ~1 across all 120 rows
    rows 120-179:  mean  ~23, varying by ~2 across all 60 rows

No scene structure. The bounded entry runs `hardware_init` plus a single render
cycle; takeover runs the real `firmware_main` loop, and only there does the scene
appear. **So bounded-run digests still cannot be trusted as evidence about what
the panel shows.** This has now bitten three separate times: it produced the
"plane untouched" readings, the "all zeros" readings, and this. Treat the panel as
ground truth and the digest as a lower bound.

### The best lead yet: row 120 of 180 is line 480 of 720

The boundary sits at exactly 2/3 height, and 2/3 of the configured
`b01c = 1280x720` is **480 lines**. If the imager's active output is 480 lines
while the CSI is configured for 720, the block assembles a frame whose lower third
is blanking -- which is precisely this shape, and would also explain why the panel
shows "part of the scene" rather than all of it.

**Next test:** read the imager's own output-height register over the software IIC
and compare against the `1280x720` the CSI expects. If they disagree, the fix is to
configure the CSI to the imager's real geometry rather than assuming the table's.
